### 3.1.2 4단계 우선순위 규칙 구현 ✅

#### 1단계: 면적(반경) 우선

**로직**:
```kotlin
// 반경이 가장 작은 위치들만 남김
val minRadius = candidates.minOf { it.radiusMeters }
var filtered = candidates.filter { it.radiusMeters == minRadius }
```

**근거**:
- 더 좁은 범위일수록 더 구체적인 위치
- 예: 집(100m) vs 동네(500m) → 집 우선

**예시**:
```
후보: [집(100m), 학교(150m), 동네(500m)]
→ 1단계 후: [집(100m)]  ✅ 확정
```

#### 2단계: 히스테리시스 (120초)

**로직**:
```kotlin
val timeSinceActivation = (System.currentTimeMillis() - lastActivationTime) / 1000

if (lastActive != null && timeSinceActivation <= HYSTERESIS_SECONDS) {
    val lastActiveInCandidates = filtered.find { it.id == lastActive }
    if (lastActiveInCandidates != null) {
        return lastActiveInCandidates  // 기존 위치 유지
    } else {
        resetHysteresis()  // 후보에서 제외 → 재평가
    }
} else if (timeSinceActivation > HYSTERESIS_SECONDS) {
    resetHysteresis()  // 만료 → 재평가
}
```

**근거**:
- 짧은 시간 내 위치 변경은 GPS 오차일 가능성
- 기존 활성 위치가 후보에 있으면 120초간 유지

**예시**:
```
상황: 집(100m)과 카페(100m)가 겹침
- 0초: 집 활성화 (히스테리시스 타이머 시작)
- 30초: 사용자가 카페 쪽으로 이동, 카페가 더 가까움
  → 히스테리시스: 집 유지 (120초 이내)
- 130초: 여전히 카페가 더 가까움
  → 히스테리시스 만료: 카페로 전환 ✅
```

#### 3단계: 거리 우선

**로직**:
```kotlin
val distances = filtered.map { location ->
    val targetLocation = Location("").apply {
        latitude = location.latitude
        longitude = location.longitude
    }
    val distance = currentLocation.distanceTo(targetLocation)
    location to distance
}

val minDistance = distances.minOf { it.second }
filtered = distances.filter { it.second == minDistance }.map { it.first }
```

**근거**:
- 사용자에게 가장 가까운 위치가 의도에 가장 부합
- Android Location API의 `distanceTo()` 사용

**예시**:
```
후보: [집(100m, 거리 50m), 학교(100m, 거리 80m)]
→ 3단계 후: [집(100m, 거리 50m)]  ✅ 확정
```

#### 4단계: 최근 수정(updatedAt) 우선

**로직**:
```kotlin
val winner = filtered.maxByOrNull { it.updatedAt }  // Phase 0에서 추가된 필드
```

**근거**:
- 최근에 수정한 위치가 사용자의 최신 의도를 반영
- Phase 0에서 추가된 `updatedAt` 필드 활용

**예시**:
```
후보: [집A(수정: 10:00), 집B(수정: 14:00)]
→ 4단계 후: [집B]  ✅ 확정 (더 최근에 수정)
```

### 3.1.3 히스테리시스 타이머 관리 ✅

#### recordActivation() 메서드

**목적**: 새 위치 활성화 시 히스테리시스 타이머 리셋

```kotlin
fun recordActivation(locationId: String) {
    val previousLocation = lastActiveLocationId
    lastActiveLocationId = locationId
    lastActivationTime = System.currentTimeMillis()
    
    if (previousLocation != locationId) {
        Log.d(TAG, "📝 Location switched: $previousLocation → $locationId (timer reset)")
    } else {
        Log.d(TAG, "📝 Same location re-activated: $locationId (timer reset)")
    }
}
```

**동작**:
1. 이전 위치와 비교하여 전환 여부 판단
2. 새 위치 ID 저장
3. 현재 시각 저장 (타이머 시작)
4. 전환 여부에 따라 로그 메시지 다르게 출력

**호출 시점**:
- `ScheduleGroupManager.activateGroupByLocation()` 성공 후
- 동일한 위치를 재활성화하는 경우에도 호출 (타이머 리셋)

#### resetHysteresis() 메서드

**목적**: 히스테리시스 상태 초기화

```kotlin
fun resetHysteresis() {
    lastActiveLocationId = null
    lastActivationTime = 0
    Log.d(TAG, "🔄 Hysteresis reset")
}
```

**호출 시점**:
1. 직전 활성 위치가 후보에서 제외됨
2. 히스테리시스 시간 만료 (120초 초과)

**효과**:
- 다음 충돌 해소 시 3단계(거리 우선)부터 평가

#### 디버깅 API

**getLastActiveLocationId()**:
```kotlin
fun getLastActiveLocationId(): String? = lastActiveLocationId
```
- 현재 히스테리시스 대상 위치 조회

**getRemainingHysteresisSeconds()**:
```kotlin
fun getRemainingHysteresisSeconds(): Long {
    if (lastActiveLocationId == null) return 0
    
    val elapsed = (System.currentTimeMillis() - lastActivationTime) / 1000
    val remaining = HYSTERESIS_SECONDS - elapsed
    
    return if (remaining > 0) remaining else 0
}
```
- 히스테리시스 남은 시간 조회 (초 단위)
- 만료 시 0 반환

## 기술적 의사결정

### 1. Singleton 패턴 사용

**결정**: `@Singleton` 어노테이션 사용

**근거**:
- 히스테리시스 상태를 앱 전역에서 단일 인스턴스로 관리
- 메모리 효율성 (인스턴스 중복 생성 방지)
- Hilt가 생명주기 자동 관리

**대안 검토**:
- 별도 상태 저장소 사용: 오버엔지니어링
- Activity/Service 스코프: 생명주기 관리 복잡

### 2. 히스테리시스 시간 120초

**결정**: `HYSTERESIS_SECONDS = 120` (2분)

**근거**:
- GPS 오차로 인한 잦은 전환 방지
- 사용자 경험: 2분은 위치 전환 의도를 판단하기 적절한 시간
- 스케줄가동프로세스.md 명세 준수

**대안 검토**:
- 60초: 너무 짧아 GPS 오차에 민감
- 180초: 너무 길어 실제 위치 전환 반응 느림

### 3. Android Location API 사용

**결정**: `Location.distanceTo()` 사용

**근거**:
- Android 표준 API로 정확도 보장
- Haversine 공식 기반 (지구 곡률 고려)
- 추가 라이브러리 불필요

**대안 검토**:
- 유클리드 거리: 지구 곡률 미반영으로 부정확
- Google Maps API: 오버헤드 큼, 의존성 증가

### 4. 상세한 로깅

**결정**: 각 단계별 상세 로그 출력

**근거**:
- 충돌 해소는 디버깅이 어려운 로직
- 실제 동작 확인 필수
- 프로덕션에서도 `Log.d()` 레벨로 안전

- 초기 설계 시 향후 확장 가능성을 고려하여 Context 주입
- 실제 구현에서는 Android Location API만 사용하여 Context 불필요

**해결**:

```kotlin
// Before
@Singleton
class LocationConflictResolver @Inject constructor(
    @ApplicationContext private val context: Context
) {
    // context를 전혀 사용하지 않음
}

// After (리뷰 반영)
@Singleton
class LocationConflictResolver @Inject constructor() {
    // 불필요한 의존성 제거
}
```

**개선 효과**:
- ✅ 의존성 최소화 (의존성 주입 원칙 준수)
- ✅ 메모리 효율성 향상 (불필요한 참조 제거)

#### 지적 사항 2: 불필요한 suspend 함수

**문제**: `resolveConflict`가 `suspend fun`으로 선언되었지만 내부에 일시중단 호출이 없음

**리뷰어 코드 참조**:
- `LocationConflictResolver.kt:52-123`

**검토 결과**: ✅ **타당함**

**원인**:
- Phase 3.2 통합 시 Repository 호출을 고려하여 사전에 `suspend` 추가
- 실제로는 모든 연산이 동기적으로 처리 가능

**해결**:
```kotlin
// Before
suspend fun resolveConflict(
    currentLocation: Location,
    candidates: List<LocationBasedAutoRun>
): LocationBasedAutoRun? {
    // 내부에 suspend 호출 없음
}

// After (리뷰 반영)
fun resolveConflict(
    currentLocation: Location,
    candidates: List<LocationBasedAutoRun>
): LocationBasedAutoRun? {
    // 일반 함수로 변경
}
```

**개선 효과**:
- ✅ 호출 측 제약 감소 (코루틴 스코프 불필요)
- ✅ 성능 향상 (코루틴 오버헤드 제거)
- ✅ 명확성 향상 (실제 동작과 시그니처 일치)

**호출부 영향**:
- Phase 3.2에서 `ScheduleGroupManager.activateGroupByLocation()`에서 호출 예정
- 해당 메서드는 이미 `suspend fun`이므로 영향 없음
- 단지 내부에서 `resolveConflict()` 호출 시 `suspend` 키워드 제거만 필요
