## 3. ScheduleGroup 엔티티 설계 검증

### 3.1 ScheduleGroup 개념

**목적**: 여러 TimeBasedAutoRun을 그룹으로 묶어 LocationBasedAutoRun과 연계

**핵심 기능**:
1. **시간표 그룹화**: 여러 시간 기반 자동 실행을 하나의 그룹으로 관리
2. **위치 기반 활성화**: 특정 위치 진입 시 그룹 전체 활성화
3. **위치 이탈 비활성화**: 위치 이탈 시 그룹 전체 비활성화
4. **독립 실행 모드**: 시간 기반 자동 실행의 독립 실행 또는 그룹 종속 선택

### 3.2 ScheduleGroup 엔티티 설계

```kotlin
/**
 * 스케줄 그룹 엔티티
 *
 * 여러 TimeBasedAutoRun을 그룹으로 묶어 위치 기반으로 활성화/비활성화합니다.
 *
 * ## 사용 예시
 * 1. "업무 시간표" 그룹 생성
 * 2. 오전 10시, 오후 2시, 오후 4시 TimeBasedAutoRun 추가 (scheduleGroupId 설정)
 * 3. "회사" LocationBasedAutoRun에 linkedScheduleGroupId 설정
 * 4. 회사 진입 → "업무 시간표" 그룹 활성화 → 3개 알람 등록
 * 5. 회사 이탈 → "업무 시간표" 그룹 비활성화 → 3개 알람 취소
 *
 * @property id 고유 ID (UUID)
 * @property name 그룹 이름 (예: "업무 시간표", "공부 루틴")
 * @property description 그룹 설명 (옵션)
 * @property isActive 활성화 여부
 * @property createdAt 생성 시간 (timestamp)
 */
@Entity(
    tableName = "schedule_group",
    indices = [Index(value = ["isActive"])]
)
data class ScheduleGroup(
    @PrimaryKey val id: String = UUID.randomUUID().toString(),
    val name: String,
    val description: String? = null,
    val isActive: Boolean = true,
    val createdAt: Long = System.currentTimeMillis()
)
```

**설계 결정사항**:
- **최대 개수 제한 없음**: 사용자가 원하는 만큼 그룹 생성 가능
- **단순 구조**: 그룹 자체는 최소 정보만 보유 (name, description, isActive)
- **인덱스**: `isActive` 필드 인덱스 (활성화된 그룹만 빠르게 조회)

### 3.3 기존 엔티티 확장 설계

#### 3.3.1 TimeBasedAutoRun 확장
```kotlin
data class TimeBasedAutoRun(
    // ... 기존 필드 ...
    
    /**
     * 연결된 ScheduleGroup ID (v5+)
     *
     * null: 독립 실행 모드 (기본값)
     * UUID: 해당 그룹에 종속
     */
    val scheduleGroupId: String? = null,
    
    /**
     * 독립 실행 여부 (v5+)
     *
     * true: scheduleGroupId와 무관하게 항상 실행 (기본값)
     * false: scheduleGroupId 그룹 활성화 시에만 실행
     *
     * 참고: scheduleGroupId가 null이면 이 필드는 무시됨 (항상 독립 실행)
     */
    val isIndependent: Boolean = true
)
```

**설계 의도**:
- `scheduleGroupId == null`: 기존 동작 유지 (항상 활성화)
- `scheduleGroupId != null && isIndependent == true`: 그룹에 속하지만 독립 실행
- `scheduleGroupId != null && isIndependent == false`: 그룹 활성화 시에만 실행

**마이그레이션 전략**:
- 기존 TimeBasedAutoRun 레코드는 `scheduleGroupId = null, isIndependent = true`로 설정
- 기존 동작에 영향 없음

#### 3.3.2 LocationBasedAutoRun 확장
```kotlin
data class LocationBasedAutoRun(
    // ... 기존 필드 ...
    
    /**
     * 연결된 ScheduleGroup ID (v5+)
     *
     * null: 1회성/주기적 트리거 (기존 동작)
     * UUID: 해당 그룹의 시간표 활성화/비활성화
     */
    val linkedScheduleGroupId: String? = null
)
```

**설계 의도**:
- `linkedScheduleGroupId == null`: 기존 동작 유지 (단순 트리거)
- `linkedScheduleGroupId != null`: 진입 시 그룹 활성화, 이탈 시 그룹 비활성화

**마이그레이션 전략**:
- 기존 LocationBasedAutoRun 레코드는 `linkedScheduleGroupId = null`로 설정
- 기존 동작에 영향 없음

### 3.4 관계 다이어그램

```
ScheduleGroup (1) ─────┐
                       │
                       │ linkedScheduleGroupId
                       ▼
LocationBasedAutoRun (N)
                       
                       
ScheduleGroup (1) ─────┐
                       │
                       │ scheduleGroupId
                       ▼
TimeBasedAutoRun (N)
```

**관계 타입**:
- `ScheduleGroup : LocationBasedAutoRun` = 1:N (하나의 그룹에 여러 위치 연결 가능)
- `ScheduleGroup : TimeBasedAutoRun` = 1:N (하나의 그룹에 여러 시간표 포함 가능)

**참조 무결성**:
- **Soft Reference**: FK 없음 (원본 그룹 삭제 시 자동 실행 설정은 독립 모드로 전환)
- **이유**: 사용자가 그룹을 삭제해도 개별 자동 실행 설정은 유지되어야 함

## 4. v4→v5 마이그레이션 복잡도 평가

### 4.1 마이그레이션 범위

#### 4.1.1 신규 테이블
- `schedule_group` 테이블 생성
- 인덱스: `(isActive)`

#### 4.1.2 기존 테이블 확장
- `time_based_auto_run` 테이블:
  - `scheduleGroupId TEXT` 추가 (nullable)
  - `isIndependent INTEGER NOT NULL DEFAULT 1` 추가
  - 인덱스: `(scheduleGroupId)` 추가
  
- `location_based_auto_run` 테이블:
  - `linkedScheduleGroupId TEXT` 추가 (nullable)
  - 인덱스: `(linkedScheduleGroupId)` 추가

### 4.2 복잡도 평가

#### 4.2.1 낮은 복잡도 요소 ✅
1. **신규 테이블 생성**: ScheduleGroup 테이블은 독립적으로 생성 가능
2. **nullable 필드 추가**: 기존 데이터에 영향 없음 (기본값 NULL)
3. **NOT NULL 필드 추가**: `isIndependent`는 DEFAULT 1로 설정 가능
4. **인덱스 생성**: 성능 향상, 데이터 영향 없음

#### 4.2.2 중간 복잡도 요소 ⚠️
1. **Soft Reference 관계**: FK 없이 애플리케이션 레벨에서 관리
   - **장점**: 마이그레이션 단순, 롤백 쉬움
   - **단점**: 참조 무결성은 애플리케이션이 보장해야 함

2. **기존 데이터 마이그레이션**: 모든 기존 레코드에 새 필드 추가
   - **예상 레코드 수**: TimeBasedAutoRun ≤ 100개, LocationBasedAutoRun ≤ 50개 (사용자당)
   - **영향도**: 낮음 (ALTER TABLE 자동 처리)

#### 4.2.3 위험 요소 ⚠️
1. **테스트 복잡도**: GeofenceTransitionsReceiver 확장 로직 테스트 필요
2. **동시성 문제**: 위치 진입/이탈 시 여러 알람 등록/취소 처리
3. **AlarmManager 제한**: Android 13+ 정확한 알람 권한 필요

### 4.3 마이그레이션 SQL 미리보기

```sql
-- 1. ScheduleGroup 테이블 생성
CREATE TABLE IF NOT EXISTS schedule_group (
    id TEXT PRIMARY KEY NOT NULL,
    name TEXT NOT NULL,
    description TEXT,
    isActive INTEGER NOT NULL DEFAULT 1,
    createdAt INTEGER NOT NULL
);

CREATE INDEX IF NOT EXISTS index_schedule_group_isActive 
ON schedule_group(isActive);

-- 2. LocationBasedAutoRun 확장
ALTER TABLE location_based_auto_run 
ADD COLUMN linkedScheduleGroupId TEXT;

CREATE INDEX IF NOT EXISTS index_location_based_auto_run_linkedScheduleGroupId 
ON location_based_auto_run(linkedScheduleGroupId);

-- 3. TimeBasedAutoRun 확장
ALTER TABLE time_based_auto_run 
ADD COLUMN scheduleGroupId TEXT;

ALTER TABLE time_based_auto_run 
ADD COLUMN isIndependent INTEGER NOT NULL DEFAULT 1;

CREATE INDEX IF NOT EXISTS index_time_based_auto_run_scheduleGroupId 
ON time_based_auto_run(scheduleGroupId);
```

**예상 실행 시간**: < 100ms (사용자당 레코드 수가 적음)

## 6. 마이그레이션 롤백 전략

### 6.1 자동 롤백 (Room 기본 동작)

**Room의 마이그레이션 실패 처리**:
```kotlin
Room.databaseBuilder(context, DetoxyDatabase::class.java, "detoxy_database")
    .addMigrations(MIGRATION_4_5)
    // .fallbackToDestructiveMigration() ❌ 사용하지 않음 (데이터 보존)
    .build()
```

- **마이그레이션 실패 시**: Room이 예외 발생 → 앱 크래시 → 사용자에게 안내
- **데이터 보존**: v4 DB 백업 자동 유지 (Room 내부 기능)

### 6.2 수동 롤백 시나리오

#### 6.2.1 시나리오 1: 마이그레이션 성공, 런타임 오류 발견
**증상**: 위치 진입 시 알람 등록 실패, 그룹 활성화 로직 오류

**롤백 방법**:
1. 앱 버전 롤백 (v0.6으로 다운그레이드)
2. Room은 v4 스키마 사용 (v5 필드 무시)
3. **문제점**: v5에서 생성한 ScheduleGroup 데이터는 v4에서 보이지 않음
   - **영향도**: 낮음 (신규 기능이므로 사용자가 적음)

#### 6.2.2 시나리오 2: 마이그레이션 중 실패
**증상**: 앱 실행 불가, DB 오픈 실패

**롤백 방법**:
1. Crashlytics로 마이그레이션 오류 로그 수집
2. 사용자에게 앱 재설치 안내 (데이터 백업 후)
3. **데이터 손실 방지**: v4 DB 백업 파일 복원 (Room 자동 백업)

## 7. 성능 영향도 측정

### 7.1 마이그레이션 성능

#### 7.1.1 예상 실행 시간
- **ScheduleGroup 테이블 생성**: < 10ms
- **ALTER TABLE 3회**: < 30ms (각 10ms)
- **인덱스 생성 3개**: < 30ms (각 10ms)
- **총 예상 시간**: < 100ms

**근거**:
- SQLite ALTER TABLE은 테이블 크기에 비례
- 사용자당 TimeBasedAutoRun ≤ 10개, LocationBasedAutoRun ≤ 5개
- 인덱스 생성은 레코드 수에 비례 (15개 이하 → 빠름)

#### 7.1.2 메모리 사용량
- **추가 메모리**: 약 1KB 미만
  - ScheduleGroup: 200 bytes/개 × 5개 = 1KB
  - 신규 인덱스: 100 bytes/개 × 3개 = 300 bytes

### 7.2 런타임 성능

#### 7.2.1 조회 성능
**기존 쿼리** (영향 없음):
```sql
SELECT * FROM time_based_auto_run WHERE isEnabled = 1 
ORDER BY hour, minute
```
- **인덱스**: `(isEnabled)`, `(hour, minute)` 사용

## 8. 설계 결정사항 요약

### 8.1 핵심 결정사항

#### 8.1.1 Soft Reference 관계 (FK 없음)
**결정**: ScheduleGroup 삭제 시 TimeBasedAutoRun/LocationBasedAutoRun은 독립 모드로 전환

**이유**:
- 사용자가 그룹을 삭제해도 개별 자동 실행 설정은 유지되어야 함
- 마이그레이션 롤백이 쉬움
- 애플리케이션 레벨에서 참조 무결성 보장 (ViewModel)

**트레이드오프**:
- 장점: 마이그레이션 단순, 롤백 쉬움
- 단점: 참조 무결성은 코드로 관리 (테스트 필요)

#### 8.1.2 isIndependent 플래그
**결정**: TimeBasedAutoRun에 `isIndependent` 필드 추가

**이유**:
- 그룹에 속하면서도 독립 실행하는 시나리오 지원
- 예: "매일 오전 9시"는 항상 실행 + "업무 시간표"에도 포함

**사용 예시**:
- `scheduleGroupId != null && isIndependent == true`: 항상 실행 (그룹 무관)
- `scheduleGroupId != null && isIndependent == false`: 그룹 활성화 시에만 실행

#### 8.1.3 nullable 필드 사용
**결정**: `scheduleGroupId`, `linkedScheduleGroupId` nullable

**이유**:
- 기존 레코드에 영향 없음 (NULL = 기존 동작)
- 신규 레코드만 그룹 ID 설정
- 마이그레이션 간단 (ALTER TABLE ADD COLUMN)

### 8.2 대안 검토 및 기각

#### 8.2.1 대안 1: Many-to-Many 관계 (중간 테이블)
```sql
CREATE TABLE schedule_group_time_based (
    scheduleGroupId TEXT,
    timeBasedAutoRunId TEXT,
    PRIMARY KEY (scheduleGroupId, timeBasedAutoRunId)
)
```

**기각 이유**:
- 복잡도 증가 (조인 쿼리 필요)
- 마이그레이션 복잡
- 현재 요구사항에는 과도한 설계

#### 8.2.2 대안 2: Foreign Key 사용
```sql
ALTER TABLE time_based_auto_run 
ADD COLUMN scheduleGroupId TEXT,
FOREIGN KEY (scheduleGroupId) REFERENCES schedule_group(id) ON DELETE SET NULL
```

**기각 이유**:
- SQLite는 ALTER TABLE에서 FK 추가 불가
- 테이블 재생성 필요 (복잡한 마이그레이션)
- Soft Reference로 충분

## 11. 기술적 학습 내용

### 11.1 Room 마이그레이션 Best Practices
1. **nullable 필드 사용**: 기존 데이터 영향 최소화
2. **DEFAULT 값 설정**: NOT NULL 필드는 DEFAULT 필수
3. **인덱스 전략**: 조회 조건이 될 필드에만 인덱스 생성
4. **Soft Reference**: 복잡한 관계는 FK 없이 애플리케이션 레벨 관리

### 11.2 SQLite ALTER TABLE 제약사항
- **지원**: ADD COLUMN (nullable or DEFAULT)
- **미지원**: ADD COLUMN with FK, DROP COLUMN, RENAME COLUMN (v3.25.0 이전)
- **대안**: 테이블 재생성 (복잡함, 피하는 것이 좋음)

### 11.3 Android AlarmManager 제한사항
- Android 13+ (API 33): `SCHEDULE_EXACT_ALARM` 권한 필요
- 권한 없으면: `setExact()` → `set()` (부정확)
- 위치 진입 시 여러 알람 등록 → 권한 확인 중요
