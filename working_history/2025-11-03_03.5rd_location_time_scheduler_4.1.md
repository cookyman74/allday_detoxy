#### 4.1.2 activateDefaultPolicy() 메서드 구현 ✅

**메서드 시그니처**:
```kotlin
suspend fun activateDefaultPolicy(): Result<Unit>
```

**처리 흐름**:
```kotlin
suspend fun activateDefaultPolicy(): Result<Unit> = runCatching {
    Log.i(TAG, "🔄 Evaluating 'anywhere' schedule policy")
    
    // 1. 모든 스케줄 그룹 조회
    val allGroups = repository.getAll().first()
    
    // 2. "어디서나 적용" 스케줄만 필터링 (linkedScheduleGroupId == null)
    val nonLocationGroups = allGroups.filter { group ->
        val linkedLocations = repository.getLinkedLocations(group.id)
        linkedLocations.isEmpty()
    }
    
    if (nonLocationGroups.isEmpty()) {
        Log.d(TAG, "ℹ️ No applicable 'anywhere' schedule")
        return Result.success(Unit)
    }
    
    // 3. 현재 시각/요일에 맞는 스케줄 필터링
    val now = LocalDateTime.now()
    val currentDay = now.dayOfWeek
    val currentTime = now.toLocalTime()
    
    val applicableCandidates = nonLocationGroups.filter { group ->
        val timeSlots = repository.getLinkedTimeBasedAutoRuns(group.id)
        timeSlots.any { slot ->
            // 요일 체크
            val enabledDaysSet = parseEnabledDays(slot.enabledDays)
            val currentDayCode = dayOfWeekToCode(currentDay)
            val daysEnabled = enabledDaysSet.contains(currentDayCode)
            
            // 시간대 체크
            val slotStart = LocalTime.of(slot.hour, slot.minute)
            val slotEnd = slotStart.plusMinutes(slot.durationMinutes.toLong())
            val inTimeRange = !currentTime.isBefore(slotStart) && !currentTime.isAfter(slotEnd)
            
            daysEnabled && inTimeRange
        }
    }
    
    if (applicableCandidates.isEmpty()) {
        Log.d(TAG, "ℹ️ No applicable 'anywhere' schedule for current time/day")
        return Result.success(Unit)
    }
    
    // 4. 우선순위 적용 (2개 이상일 때)
    val selectedPolicy = if (applicableCandidates.size == 1) {
        applicableCandidates.first()
    } else {
        selectByPriority(applicableCandidates)
    }
    
    // 5. "어디서나 적용" 스케줄 활성화
    repository.toggleActiveWithTimestamp(selectedPolicy.id, true, System.currentTimeMillis())
    
    // 6. 알람 등록
    val timeSlots = repository.getLinkedTimeBasedAutoRuns(selectedPolicy.id)
    timeSlots.filter { it.isEnabled }.forEach { slot ->
        alarmManager.scheduleTimeBasedAutoRun(slot)
    }
    
    Log.i(TAG, "✅ 'Anywhere' schedule activated: ${selectedPolicy.name}")
}
```

**주요 특징**:
1. **"어디서나 적용" 스케줄 식별**
   - 위치 기반 자동 실행이 연결되지 않은 그룹
   - `getLinkedLocations().isEmpty()` 조건

2. **현재 시각/요일 기반 필터링**
   - 현재 시각이 시간대 범위 내인지 확인
   - 현재 요일이 활성화된 요일인지 확인
   - LocalTime 비교: `!currentTime.isBefore(slotStart) && !currentTime.isAfter(slotEnd)`

3. **조기 반환**
   - "어디서나 적용" 스케줄 없음 → Success
   - 현재 시각/요일에 맞는 스케줄 없음 → Success

#### 4.1.3 selectByPriority() 메서드 구현 ✅

**메서드 시그니처**:
```kotlin
private suspend fun selectByPriority(candidates: List<ScheduleGroup>): ScheduleGroup
```

**우선순위 규칙** (기반: 스케줄가동프로세스.md):
1. **더 구체적인 스케줄 (평일 > 매일, 주말 > 매일)**
2. **최근 수정(updatedAt) 우선** (TODO: Phase 0 완료 후)
3. **생성 순서(createdAt) 우선**

**구현**:
```kotlin
private suspend fun selectByPriority(candidates: List<ScheduleGroup>): ScheduleGroup {
    Log.d(TAG, "━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━")
    Log.d(TAG, "🔍 Priority Selection Start")
    
    // 1. 구체성 점수 계산
    val scored = candidates.map { group ->
        val timeSlots = repository.getLinkedTimeBasedAutoRuns(group.id)
        val specificityScore = calculateSpecificityScore(timeSlots)
        group to specificityScore
    }
    
    Log.d(TAG, "📊 Specificity scores:")
    scored.forEach { (group, score) ->
        Log.d(TAG, "  - ${group.name}: $score")
    }
    
    val maxScore = scored.maxOf { it.second }
    var filtered = scored.filter { it.second == maxScore }.map { it.first }
    
    if (filtered.size == 1) {
        val winner = filtered.first()
        Log.d(TAG, "✅ Winner: ${winner.name} (specificity)")
        Log.d(TAG, "━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━")
        return winner
    }
    
    Log.d(TAG, "🔄 Tie-breaking: ${filtered.size} schedules with same specificity")
    
    // 2. 최근 수정 우선 (TODO: updatedAt 필드 추가 시)
    
    // 3. 생성 순서 우선
    val winner = filtered.maxByOrNull { it.createdAt }!!
    Log.d(TAG, "✅ Winner: ${winner.name} (created at: ${winner.createdAt})")
    Log.d(TAG, "━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━")
    
    return winner
}
```

**동작 방식**:
1. 각 후보의 구체성 점수 계산
2. 최고 점수를 가진 후보들만 필터링
3. 필터링 결과가 1개면 즉시 반환
4. 2개 이상이면 `createdAt` 기준으로 최신 선택

#### 4.1.4 calculateSpecificityScore() 메서드 구현 ✅

**메서드 시그니처**:
```kotlin
private fun calculateSpecificityScore(timeSlots: List<TimeBasedAutoRun>): Int
```

**점수 체계**:
| 활성화 요일 | 조건 | 점수 | 설명 |
|------------|------|------|------|
| 7일 | 매일 | 1점 | 가장 일반적 |
| 5일 | 평일 (월~금) | 2점 | 구체적 |
| 5일 | 기타 5일 | 3점 | 더 구체적 |
| 2일 | 주말 (토~일) | 2점 | 구체적 |
| 2일 | 기타 2일 | 3점 | 더 구체적 |
| 그 외 | 특정 요일만 | 3점 | 가장 구체적 |

**구현**:
```kotlin
private fun calculateSpecificityScore(timeSlots: List<TimeBasedAutoRun>): Int {
    if (timeSlots.isEmpty()) {
        return 1  // 시간대 없음 = 가장 일반적
    }
    
    // 모든 시간대의 활성화 요일을 합침
    val allDays = timeSlots.flatMap { parseEnabledDays(it.enabledDays) }.distinct()
    
    return when (allDays.size) {
        7 -> 1  // 매일
        5 -> {
            val weekdayCodes = setOf("MON", "TUE", "WED", "THU", "FRI")
            val isWeekday = allDays.containsAll(weekdayCodes)
            if (isWeekday) 2 else 3
        }
        2 -> {
            val weekendCodes = setOf("SAT", "SUN")
            val isWeekend = allDays.containsAll(weekendCodes)
            if (isWeekend) 2 else 3
        }
        else -> 3  // 특정 요일만
    }
}
```

**계산 방식**:
1. 모든 시간대의 활성화 요일을 합쳐서(distinct) 전체 활성화 요일 수 구하기
2. 요일 수와 조합에 따라 점수 부여
3. 높은 점수 = 더 구체적

#### 4.1.5 유틸리티 메서드 구현 ✅

**1) parseEnabledDays() - JSON 문자열 파싱**:
```kotlin
private fun parseEnabledDays(enabledDaysJson: String): Set<String> {
    if (enabledDaysJson.isBlank() || enabledDaysJson == "[]") {
        return emptySet()
    }
    
    return try {
        // 간단한 JSON 파싱 (정규식 사용)
        val regex = Regex(""""(\w+)"""")
        regex.findAll(enabledDaysJson)
            .map { it.groupValues[1].uppercase() }
            .filter { it in VALID_DAY_CODES }
            .toSet()
    } catch (e: Exception) {
        Log.e(TAG, "❌ Failed to parse enabledDays: $enabledDaysJson", e)
        emptySet()
    }
}
```

**입력 예시**: `"[\"MON\",\"TUE\",\"WED\"]"`  
**출력 예시**: `setOf("MON", "TUE", "WED")`

**2) dayOfWeekToCode() - DayOfWeek 변환**:
```kotlin
private fun dayOfWeekToCode(dayOfWeek: DayOfWeek): String {
    return when (dayOfWeek) {
        DayOfWeek.MONDAY -> "MON"
        DayOfWeek.TUESDAY -> "TUE"
        DayOfWeek.WEDNESDAY -> "WED"
        DayOfWeek.THURSDAY -> "THU"
        DayOfWeek.FRIDAY -> "FRI"
        DayOfWeek.SATURDAY -> "SAT"
        DayOfWeek.SUNDAY -> "SUN"
    }
}
```

## 기술적 의사결정

### 1. enabledDays JSON 파싱 방식

**문제**: `TimeBasedAutoRun.enabledDays`가 JSON 문자열 (`String`) 타입으로 저장됨

**검토된 방법**:
1. ✅ **정규식 파싱** (채택)
   - 장점: 간단하고 빠름, 외부 라이브러리 불필요
   - 단점: JSON 구조 변경 시 취약
   - 근거: 기존 코드베이스에서 동일한 방식 사용 중 (AutoRunAlarmManager, NextAutoRunCalculator 등)

2. ❌ Gson 라이브러리 사용
   - 장점: 안전하고 정확
   - 단점: 추가 의존성, 오버헤드
   - 근거: 현재 프로젝트에 Gson 없음, 간단한 배열 파싱에 과함

3. ❌ kotlinx.serialization 사용
   - 장점: Kotlin 네이티브, 타입 안전
   - 단점: 추가 의존성 및 설정
   - 근거: 현재 프로젝트에 없음

**결론**: 
- 정규식 파싱은 기존 코드베이스와 일관성 유지
- `VALID_DAY_CODES`로 유효성 검증
- 파싱 실패 시 `emptySet()` 반환으로 안전성 확보

---

### 2. LocalTime 범위 체크 방식

**문제**: `LocalTime`에는 `in` 연산자가 없음 (ClosedRange가 아님)

**검토된 방법**:
1. ✅ **`!isBefore && !isAfter` 조합** (채택)
   - 구현: `!currentTime.isBefore(slotStart) && !currentTime.isAfter(slotEnd)`
   - 장점: 명확하고 읽기 쉬움, boundary 포함 보장
   - 단점: 다소 장황

2. ❌ `compareTo()` 사용
   - 구현: `currentTime.compareTo(slotStart) >= 0 && currentTime.compareTo(slotEnd) <= 0`
   - 장점: 간결
   - 단점: 가독성 떨어짐

3. ❌ extension function 생성
   - 구현: `fun LocalTime.isBetween(start: LocalTime, end: LocalTime): Boolean`
   - 장점: 재사용 가능
   - 단점: 단일 클래스에서만 사용, 오버엔지니어링

**결론**:
- `!isBefore && !isAfter`가 가장 명확하고 의도를 잘 표현
- Boundary 포함 여부가 명확 (start, end 모두 포함)

### 3. 구체성 점수 체계 설계

**문제**: "더 구체적인 스케줄 우선" 규칙의 구체적인 점수 산정

**설계 근거** (기반: 스케줄가동프로세스.md):
1. **7일 → 1점 (매일)**
   - 가장 일반적인 스케줄
   - 다른 모든 스케줄에 밀림

2. **5일(평일) / 2일(주말) → 2점**
   - 일반적으로 많이 사용되는 패턴
   - 매일보다 구체적

3. **특정 요일 조합 → 3점**
   - 가장 구체적
   - 사용자가 명시적으로 설정

**trade-off**:
- ✅ 단순한 3단계 체계로 명확성 확보
- ❌ 세밀한 구분은 불가 (예: 4일 vs 3일)
- 근거: 대부분의 사용 케이스 커버, 복잡도 최소화

---

### 4. 우선순위 규칙 순서

**기반**: 스케줄가동프로세스.md

**규칙 순서**:
1. 구체성 (specificity) → 명확한 의도 우선
2. 최근 수정 (updatedAt) → 사용자 최신 의도 반영 (TODO: Phase 0 완료 후)
3. 생성 순서 (createdAt) → 최신 생성 우선

**결정 근거**:
- **구체성 최우선**: 명시적 > 암묵적
- **최근 수정 2순위**: 사용자의 최신 의도
- **생성 순서 3순위**: fallback 기준

## Phase 4.1 리뷰 반영

### 리뷰 의견

#### 문제점 1: suspend 함수 호출 컨텍스트 오류 ⚠️

**지적 사항**:
- `repository.getLinkedLocations()`와 `repository.getLinkedTimeBasedAutoRuns()`는 suspend 함수
- `List.filter { … }` 블록 안에서 직접 호출 불가 (suspend 컨텍스트 아님)
- 실제로는 빌드가 성공했지만 코드 구조상 문제

**위치**: 
- `activateDefaultPolicy()` 메서드
- Line 96-141 (원본 코드)

**원인**:
```kotlin
// ❌ 잘못된 코드
val nonLocationGroups = allGroups.filter { group ->
    val linkedLocations = repository.getLinkedLocations(group.id)  // suspend 함수 호출
    linkedLocations.isEmpty()
}
```

**해결 방법**:
- `filter` 대신 `for` loop 사용
- suspend 함수를 직접 호출하고 결과를 MutableList에 추가

**수정 후**:
```kotlin
// ✅ 올바른 코드
val nonLocationGroups = mutableListOf<ScheduleGroup>()
for (group in allGroups) {
    val linkedLocations = repository.getLinkedLocations(group.id)  // suspend 함수 직접 호출
    if (linkedLocations.isEmpty()) {
        nonLocationGroups.add(group)
    }
}
```

**동일한 패턴으로 수정**:
1. "어디서나 적용" 스케줄 필터링 (getLinkedLocations)
2. 현재 시각/요일 맞는 스케줄 필터링 (getLinkedTimeBasedAutoRuns)

---

#### 문제점 2: 단일 활성화 원칙 위반 ⚠️

**지적 사항**:
- `toggleActiveWithTimestamp()`만 호출하고 알람을 직접 등록
- 기존 활성화된 다른 스케줄이 그대로 남아있음
