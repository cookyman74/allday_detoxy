## 5. Migration_4_5.kt 작성 (Day 18 오전)

**파일**: `data/local/migrations/Migration_4_5.kt`

### 5.1 마이그레이션 SQL

```sql
-- 1. ScheduleGroup 테이블 생성
CREATE TABLE IF NOT EXISTS schedule_group (
    id TEXT PRIMARY KEY NOT NULL,
    name TEXT NOT NULL,
    description TEXT,
    isActive INTEGER NOT NULL DEFAULT 1,
    createdAt INTEGER NOT NULL
);

-- 2. ScheduleGroup 인덱스 생성
CREATE INDEX IF NOT EXISTS index_schedule_group_isActive 
ON schedule_group(isActive);

-- 3. TimeBasedAutoRun 테이블 확장
ALTER TABLE time_based_auto_run 
ADD COLUMN scheduleGroupId TEXT;

ALTER TABLE time_based_auto_run 
ADD COLUMN isIndependent INTEGER NOT NULL DEFAULT 1;

-- 4. TimeBasedAutoRun 인덱스 생성
CREATE INDEX IF NOT EXISTS index_time_based_auto_run_scheduleGroupId 
ON time_based_auto_run(scheduleGroupId);

-- 5. LocationBasedAutoRun 테이블 확장
ALTER TABLE location_based_auto_run 
ADD COLUMN linkedScheduleGroupId TEXT;

-- 6. LocationBasedAutoRun 인덱스 생성
CREATE INDEX IF NOT EXISTS index_location_based_auto_run_linkedScheduleGroupId 
ON location_based_auto_run(linkedScheduleGroupId);
```

### 5.2 마이그레이션 전략

**기존 데이터 영향도**: 없음
- `scheduleGroupId`, `linkedScheduleGroupId`: NULL (nullable)
- `isIndependent`: DEFAULT 1 (기존 동작 유지)

**예상 실행 시간**: < 100ms
- ScheduleGroup 테이블 생성: < 10ms
- ALTER TABLE 3회: < 30ms
- 인덱스 생성 3개: < 30ms

## 11. 설계 결정사항 요약

### 11.1 Clean Architecture 레이어 분리

| 레이어 | 책임 | 구현 위치 |
|--------|------|----------|
| **domain** | 비즈니스 로직, 인터페이스 정의 | `domain/repository/ScheduleGroupRepository.kt` (인터페이스) |
| **data** | 데이터 저장/조회, Repository 구현 | `data/repository/ScheduleGroupRepositoryImpl.kt` (구현) |
| **presentation** | UI 상태 관리, 사용자 인터랙션 | (Week 4 구현 예정) |

**설계 이유**:
- 테스트 용이성: domain 레이어 테스트 시 MockRepository 사용 가능
- 의존성 역전: presentation → domain (인터페이스) ← data (구현)
- 확장성: 향후 서버 동기화 시 RemoteRepository 구현 추가 가능

### 11.2 Soft Reference 참조 무결성 정책

| 작업 | ScheduleGroup | TimeBasedAutoRun | LocationBasedAutoRun | AlarmManager |
|------|--------------|------------------|----------------------|--------------|
| **ScheduleGroup 삭제** | 삭제 | scheduleGroupId → NULL | linkedScheduleGroupId → NULL | 종속 알람 취소 (isIndependent == false) |
| **ScheduleGroup 비활성화** | isActive → false | isEnabled → false (isIndependent == false만) | 영향 없음 | 종속 알람 취소 |
| **TimeBasedAutoRun 삭제** | 영향 없음 | 삭제 | 영향 없음 | 해당 알람 취소 |
| **LocationBasedAutoRun 삭제** | 영향 없음 | 영향 없음 | 삭제 | Geofence 해제 |

**설계 이유**:
- 사용자 데이터 보존 우선: 그룹 삭제 시 개별 자동 실행 설정은 유지 (독립 모드로 전환)
- 명시적 참조 해제: groupId를 NULL로 설정하여 "그룹 없음" 상태 표현
- 종속 알람만 취소: 독립 실행 모드(isIndependent == true)는 그룹 삭제와 무관하게 계속 실행

### 11.3 기존 패턴 유지

**기존 Repository 구조**:
- 일부는 domain 인터페이스 + data 구현 (예: `AutoRunSettingsRepository`)
- 일부는 data 직접 구현 (예: `TimeBasedAutoRunRepository`, `LocationBasedAutoRunRepository`)

**선택한 방식**:
- **ScheduleGroup**: domain 인터페이스 + data 구현 (새로운 기능이므로 Clean Architecture 적용)
- **기존 Repository**: 그대로 유지하고 v5 메서드만 추가 (일관성 유지)

## 12. 기술적 학습 내용

### 12.1 Room 마이그레이션 Best Practices

1. **nullable 필드 사용**: 기존 데이터 영향 최소화
2. **DEFAULT 값 설정**: NOT NULL 필드는 DEFAULT 필수
3. **인덱스 전략**: 조회 조건이 될 필드에만 인덱스 생성
4. **Soft Reference**: 복잡한 관계는 FK 없이 애플리케이션 레벨 관리

### 12.2 Clean Architecture 적용

1. **인터페이스-구현 분리**: domain 레이어는 인터페이스만, data 레이어는 구현만
2. **의존성 역전**: presentation → domain (인터페이스) ← data (구현)
3. **참조 무결성**: 애플리케이션 레벨에서 Repository가 보장

### 12.3 기존 코드와의 통합

1. **일관성 유지**: 기존 DAO 확장 시 주석 패턴 유지 (`// v5 추가: ...`)
2. **기존 메서드 보존**: 기존 기능에 영향 없도록 새 메서드만 추가
3. **DI 통합**: Hilt를 통한 의존성 주입, DatabaseModule에 Provider 추가
